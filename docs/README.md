# 📚 文檔管理規範

## 📁 資料夾結構

```
docs/
├── README.md                    # 📋 本文檔（文檔管理規範）
├── architecture/                # 🏗️ 系統架構設計文檔
│   ├── minigame_system_architecture_analysis.md
│   └── multi_player_ui_system.md
├── guides/                      # 📖 使用指南與操作手冊
│   └── complete_multi_ui_test_guide.md
├── development/                 # 🔧 開發相關文檔
│   └── [開發流程、API文檔等]
└── archive/                     # 🗄️ 歸檔文檔（已解決問題的調試記錄）
    ├── 1P_display_solutions.md
    ├── 1P_position_fix_report.md
    ├── bottom_panel_diagnosis.md
    └── [各種調試和修復記錄...]
```

## 📝 文檔創建標準

### ✅ 何時創建文檔

1. **系統架構設計** → `docs/architecture/`
   - 新系統或重要功能的架構說明
   - 為其他開發者提供設計思路
   - 長期參考價值高

2. **使用指南手冊** → `docs/guides/`
   - 複雜功能的使用說明
   - 測試流程指南
   - 部署和維護手冊

3. **開發參考文檔** → `docs/development/`
   - API文檔
   - 開發流程說明
   - 編碼規範補充

### ❌ 避免創建的文檔

1. **臨時調試記錄** → 直接在代碼註釋中說明
2. **Bug修復過程** → 寫在git commit message
3. **實驗性解決方案** → 不需要正式文檔化

### 🧹 定期清理原則

- **每月檢查**: archive/ 資料夾中的過時文檔
- **6個月清理**: 移除已無參考價值的歷史記錄
- **版本更新**: 同步更新相關架構文檔

## 🎯 文檔命名規範

### 檔名規範
- 使用英文檔名（避免編碼問題）
- 小寫字母 + 底線連接：`system_architecture.md`
- 簡潔明確，反映內容主題

### 文檔結構
```markdown
# 標題

## 概覽
簡要說明文檔目的

## 具體內容
...

## 總結
重點整理
```

## 📋 維護責任

- **創建者負責**: 文檔的準確性和及時更新
- **團隊共同**: 定期清理過時文檔
- **項目負責人**: 監督文檔管理標準執行

## 🚀 文檔工具鏈

- **編輯**: 使用支持Markdown的編輯器
- **預覽**: GitHub/VS Code內建預覽功能  
- **版本控制**: 文檔與代碼統一進行git管理
- **協作**: 通過PR進行文檔審查

---

**遵循這些規範，保持文檔的整潔性和實用性！** 📚
